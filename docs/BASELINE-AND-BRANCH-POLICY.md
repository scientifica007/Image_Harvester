## سياسة التطوير القادمة
1. **لا تعديل للوسم `v0.1.1` أو إعادة وسمه**، ولا تغيير أو استبدال الحزمة المرفقة بإصداره.
2. **لا دفع تطوير جديد إلى `baseline/field-accepted-v0.1.1`**؛ يبقى مرجعًا للاستعادة والمقارنة.
3. يوضع العمل المخصص للإصدار `0.1.2` في [develop/v0.1.2](https://github.com/scientifica007/Image_Harvester/tree/develop/v0.1.2) أو فروع ميزات مشتقة منه.
4. لا تُدمج تغييرات الإصدار القادم في `main` قبل الاختبارات وموافقة مالك المشروع الصريحة؛ ويستحسن استخدام Pull Request وفحوص CI.
5. توثّق الملاحظات والمهام ذات الصلة في [خطة 0.1.2](ROADMAP-v0.1.2.md). في هذه المرحلة لا يُغيّر المحرك أو الواجهة.
6. عند الاعتماد المستقبلي لـ`0.1.2`، أنشئ وسمًا وإصدارًا جديدين دون المساس بأي من مراجع `0.1.1`.

## حدود الضمان التقني
هذه السياسة **تجميد موثّق بالتوافق التنظيمي** وليست حماية تقنية مفروضة من GitHub. وقت الإنشاء كان `main` غير محمي ولم تكن هناك Rulesets. يجب تفعيل Rule/Ruleset من **Settings → Rules → Rulesets** بصفة مالك المستودع؛ حساب GitHub المتصل بهذه المحادثة لا يتيح تعديل قواعد الحماية عبر الأدوات الحالية.

الحد الأدنى المقترح: منع الحذف وforce-push لـ`main` وللفرع المرجعي، واشتراط Pull Request وفحص CI ناجح على `main`. عند تمكين قواعد Pull Request، تأكد من عدم إعاقة تحديثات الإصدار التي ترغب بها مستقبلًا. وعندما يتاح ذلك في خطتك وإعدادات المستودع، فعّل عدم قابلية تعديل الإصدارات (Immutable Releases) لحماية وسوم الإصدارات وأصولها. تحقق من تطبيق القواعد فعليًا بعد الحفظ، ولا تعتمد على وجود هذه الوثيقة كوسيلة حماية آلية.
